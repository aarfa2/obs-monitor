OBS 机群监控系统 — 项目汇报

汇报人：Scott

汇报日期：2026 年 8 月 20 日

项目版本：v0.1.0（局域网场景已可实际使用）

适用范围：直播/录播现场多台 OBS 推流电脑的集中监控

一、摘要

本项目是一套面向生产推流机房的值班监控系统，解决「十几台 OBS 电脑分散运行、故障发现慢、排障证据散」的问题。

系统采用中心看板 + 各机轻量采集器架构：值班人员在一个网页上即可查看全部机器是否在线、是否在推流、是否存在渲染/编码/网络压力，并在异常时通过 Webhook 自动通知值班群。只监控、不控制——不能通过本系统修改 OBS 配置或停推流，避免误操作风险。

二、背景与痛点

现场典型情况：多台电脑各自用 OBS 推流到服务器，采集卡、摄像头、编码器、上行网络任一环节出问题，画面就会卡、花、停，甚至整机静默。

现状问题影响
需逐台远程桌面或到机房查看机器一多，人力跟不上
往往观众先投诉才发现故障发现滞后，影响播出质量
出事后翻各机 OBS 日志时间对不齐、容易漏、排障慢
若开放 OBS 远程控制接口存在误操作停推流等生产风险

核心需求：看得见（集中看板）→ 来得及（自动报警）→ 查得清（日志检索与掉帧分类）→ 控得住风险（监控与控制分离）。

三、建设目标

  1. 集中可视：全部 OBS 机器推流状态、健康指标一屏呈现
  2. 主动告警：停推、重连、失联等异常自动通知，不依赖人盯屏
  3. 快速定位：区分渲染掉帧、编码掉帧、网络丢帧，支持近 24 小时日志检索
  4. 安全边界：只读采集，不向 OBS 下发任何控制指令

四、系统能力与业务价值

4.1 已具备功能

模块能力说明
机群总览每台机器一张卡片：在线/离线、推流状态、重连、压力等级、码率、CPU；异常机器自动置顶
单机详情场景与源列表、码率/帧率/拥塞、三类掉帧率、录像状态、历史曲线
智能报警OBS 失联、意外停推、持续重连、采集器心跳超时；支持 Webhook（可接企业微信/钉钉）；恢复后自动发恢复通知
日志中心汇聚各机 OBS 原生日志，按分类/级别/关键字检索；敏感信息脱敏；中心保留约 24 小时

4.2 三类掉帧（排障核心指标）

比单一「GPU 占用」更有现场指导意义：

  • 渲染掉帧 → 场景过重、浏览器源、滤镜等合成压力
  • 编码掉帧 → 编码器过载
  • 网络丢帧 → 上行带宽不足或服务器侧不稳
OBS 官方接口不提供 GPU 占用数据，系统不编造该指标；渲染掉帧是判断「显卡/合成压力」的可靠依据。

4.3 业务价值

价值维度预期效果
故障发现从「观众反馈/人工巡机」→「看板变红 + 即时通知」
排障效率先看掉帧类型和日志分类，减少盲目重启和远程桌面
规模扩展10 台与 20 台同一套中心，按「一机一采集器」线性扩展
生产安全监控面与控制面分离，OBS 配置权仍在现场机

五、技术方案概要

OBS 电脑 × N              监控服务器（Hub）              值班终端
┌──────────────┐         ┌─────────────────┐         ┌──────────┐
│ OBS 推流      │         │ 网页看板         │         │ 浏览器    │
│ 采集器 Agent  │ ──WS──► │ 日志存储 + 报警  │ ◄─HTTP─ │ 机群→单机 │
│ 只连本机 OBS  │         │ 端口 8787        │         └──────────┘
└──────────────┘         └─────────────────┘

设计要点：

  • Agent（采集器）：跑在每台 OBS 电脑，无界面、轻量（约数十 MB 内存），每秒约 1 次只读查询，不装 Electron，避免与推流抢资源
  • Hub（中心）：跑在监控服务器一台，对外提供唯一看板地址，接收全部采集器数据，存日志、发 Webhook
  • 技术栈：TypeScript + Fastify（后端）+ React（看板），基于 OBS 28+ 官方 WebSocket 接口

安全设计：各机 OBS WebSocket 仅监听本机（127.0.0.1:4455），采集器只读采集后出站上报；中心不会向采集器下发控制命令。

六、部署与运维

6.1 部署方式

角色部署位置启动方式
中心 Hub监控服务器 1 台npm run build && npm start，看板 http://服务器IP:8787
采集器 Agent每台 OBS 电脑 1 个npm run start:agent，配置中心地址、Token、显示名、本机 OBS 密码

6.2 运维建议

  1. 各机 OBS WebSocket 不对公网/全域网开放，仅本机访问
  2. 采集器与中心共用 Token；每台机器自动生成唯一 ID，禁止复制到其他机器
  3. 日志默认保留 24 小时，中心上限约 20 万条，避免磁盘堆满
  4. 采集器可配置为 Windows 开机服务（NSSM / 任务计划程序）

七、风险与系统边界

7.1 明确能做到的

  • 实时监控推流状态、掉帧、源列表、OBS 日志
  • 采集器/整机失联检测（含电脑死机、进程被杀）
  • 局域网内十余台机器规模完全可承受

7.2 明确做不到的（需管理预期）

边界说明
观众端 CDN 卡顿本系统监控的是推流端，不是 CDN/播放端
每路摄像机画面监看不是多路视频监看系统，是 OBS 运行状态监控
推流服务器自身状态不能替代 RTMP/SRT 服务器侧监控
GPU 占用百分比OBS 接口不提供，系统不编造
远程控制 OBS刻意不做，避免生产事故

7.3 资源影响评估

采集器为无界面进程，约每秒 1 次轻量只读查询，正常情况下对 OBS 编码影响可忽略。

八、下一步计划（建议优先级）

优先级事项投入预期收益
P0采集器做成开机服务 + 简易安装包小便于铺到十余台，降低部署门槛
P0Webhook 接入现有值班群，约定响应流程小报警真正落地，不再依赖盯屏
P1小范围试点（3～5 台）跑一周，收集值班反馈中验证指标与报警阈值是否贴合现场
P2若需外网查看，采集器出站到固定中心中出门也能看，仍不暴露 OBS 端口
P3日志长期归档（若合规/审计需要）大需单独立项

九、结论与决策建议

项目定位：面向生产推流机房的值班监控工具，不是 OBS 美化插件，也不是导播台。

核心价值：用很小的本机占用，把「十几台机器好不好」变成可看、可查、可叫人的状态，同时把误操作风险关在门外。

建议决策：

  1. 批准在局域网内小范围试点（3～5 台 + 1 台中心服务器），验证值班流程
  2. 安排运维对接 Webhook（企业微信/钉钉等），明确「失联/停推」响应人
  3. 试点稳定后批量铺采集器，优先做成开机自启，减少人工维护
